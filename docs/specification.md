# mmm-loop — Specification

An autonomous, sprint-based agent loop for Claude Code. This document is the
source of truth for the design; code comments reference its sections
(`spec §N`). The [README](../README.md) covers installation and usage.

Inspirations: [wsff](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md),
[mattpocock/skills](https://github.com/mattpocock/skills),
[ralph](https://github.com/snarktank/ralph).

---

## 1. Overview

mmm-loop runs an unattended development loop against a target project. Each
iteration is a **sprint**: pick a focus area from the vision, write a spec,
break it into tickets, implement and review each ticket, UX-test the
sprint's delta (fixing what's worth fixing in the same sprint), produce an
HTML report with a quiz, and update the project's vision status. The loop
then halts (default: one sprint per invocation) or starts the next sprint.

A deterministic **orchestrator** (TypeScript on Bun) drives the loop. All
control flow — file validation, phase selection, ticket ordering, commit
recording, stop conditions — is plain code. LLM agents (fresh `claude -p`
processes) are used only for the creative work inside each step.

## 2. Design principles

1. **Autonomous** — runs without human intervention; humans interact only
   between runs (report, blocked tickets).
2. **Deterministic where possible** — anything checkable programmatically is
   checked by the orchestrator, never delegated to an LLM.
3. **Sequential** — each step finishes (and is validated) before the next
   starts. Within step 5, one ticket at a time.
4. **Minimal context** — each agent gets a fresh process, a purpose-built
   prompt, and only the files it needs.
5. **Focused agents** — every prompt states the agent's single purpose and
   exact expected output.
6. **Self-contained per project** — the loop's scripts and prompts are copied
   into each target project (ralph-style), so they are visible and freely
   modifiable per project.
7. **Crash-safe** — the current phase is derived from filesystem state, so the
   loop can be killed and rerun at any point without losing or orphaning work.

## 3. Distribution and installation

The mmm-loop repo contains a copyable bundle at `scripts/mmm-loop/`. To
install into a target project:

```bash
cp -r <mmm-loop-repo>/scripts/mmm-loop <target>/scripts/mmm-loop
```

Then, from the target project root:

```bash
bun scripts/mmm-loop/loop.ts init   # scaffold required files
bun scripts/mmm-loop/loop.ts run    # run one sprint
```

There is no global install and no version coupling: the copy is yours to edit.
Prompts ship inside the bundle, so per-project prompt tweaks are normal and
expected.

### Bundle layout (copied into the target project)

```
scripts/mmm-loop/
  loop.ts            # entry point: init | run
  config.ts          # per-step model / effort / max-turns table (edit freely)
  lib/               # orchestrator internals (phase derivation, spawn wrapper, ...)
  prompts/
    02-sprint-focus.md
    03-spec.md
    03-cleanup-identify.md
    04-tickets.md
    04-cleanup-tickets.md
    05-implement.md
    05-review.md
    05.5-ux-plan.md
    05.5-ux-test.md
    05.5-ux-tickets.md
    06-report.md
    07-vision-status.md
```

## 4. Target project layout

```
docs/
  CONTEXT.md               # always-relevant context for every agent (human-authored)
  vision.md                # what to build (human-authored)
  sprint_reports.html      # generated by step 6 (not required by validation)
  ...                      # optionally other human docs
.working/                  # the loop's memory — tracked in git, NOT gitignored
  vision_status.md         # current state of the project vs the vision
  learnings.md             # append-only one-liners (gotchas, conventions)
  sprints/
    01-mvp/
      sprint_focus.md
      spec.md
      ux_test_plan.md                  # generated by step 5.5.1
      ux_findings.md                   # generated by step 5.5.2
      tickets/
        001-first-thing.json
        001.1-fix-first-thing.json     # optional review fix ticket
        002-second-thing.json
        003-ux-fix-help.json           # optional UX ticket (step 5.5.3)
```

- Sprint folders: `NN-slug` — two-digit zero-padded number + kebab-case slug,
  so lexical sort equals numeric sort. `NN` = existing sprint folder count + 1.
  A **cleanup sprint** (§8.8) is exactly `NN-cleanup` and has no
  `sprint_focus.md` — the folder name is the focus; `cleanup` is therefore a
  reserved slug for normal sprints (§6.1).
- Ticket files: `NNN-slug.json` (three-digit). Execution order = filename
  order. Fix tickets are `NNN.1-slug.json`, which sorts directly after the
  parent (`003-x.json` < `003.1-fix-x.json` < `004-y.json`); the filename
  itself encodes parentage — there is no `parent` field.

## 5. CLI

### `init`

Scaffolds the required files with template content (headings plus TODO
placeholders and short suggestions of what to write). Never overwrites an
existing file. Creates:

- `docs/CONTEXT.md`
- `docs/vision.md`
- `.working/vision_status.md` (template from §8.7, stating nothing is built yet)
- `.working/learnings.md` (empty with a one-line header)

### `run [--max-sprints N] [--cleanup]`

Runs the loop. Default `--max-sprints 1`: one full sprint, then exit. Higher
values chain sprints (e.g. `--max-sprints 3` for an overnight run) — but a
sprint that ends with blocked tickets always halts the run (§9), regardless of
sprints remaining.

Two independent triggers make a newly *created* sprint a **cleanup sprint**
(§8.8):

- **Flag**: `--cleanup` forces the first sprint created during the run. If
  the run only resumes and finishes an in-progress sprint without creating a
  new one, the flag has no effect and the orchestrator prints a notice saying
  so. (On a blocked exit-2 run the notice is skipped — state is derivable;
  just pass the flag again.) Subsequent sprints in the same run follow the
  cadence rule.
- **Cadence**: `CLEANUP_CADENCE` in `config.ts` (the spec name is
  `cleanupCadence`; default `3`, `0` = disabled). A newly created sprint `NN`
  is a cleanup sprint iff `NN % cadence === 0` — stateless, derivable from
  the sprint number alone. The default gives sprints 03, 06, 09, …

`--cleanup` wins over cadence for the sprint it applies to. The two can
produce consecutive cleanup sprints (e.g. 02 forced, 03 by cadence); that is
accepted, not prevented — a forced cleanup does not reset the cadence.

### Allowed Claude user

`config.ts` can pin `run` to one Claude account:

```ts
/**
 * Only run when the logged-in Claude account has this email address
 * (case-insensitive). null = accept any account. Overridable with the
 * MMM_LOOP_ALLOWED_CLAUDE_USER env var (env wins; used by tests).
 */
export const ALLOWED_CLAUDE_USER: string | null = null;
```

The default `null` skips the check entirely — zero cost when unused. When
set, step 1 (§8.1) refuses to start as any other account: the loop burns
real tokens unattended, and running overnight on the wrong login (work vs.
personal) bills the wrong subscription. The env var
`MMM_LOOP_ALLOWED_CLAUDE_USER` overrides the constant when set (same idiom
as `MMM_LOOP_CLAUDE_BIN`); an empty-string value means "accept any" — an
explicit off-switch for one run. `init` does not check (it spawns no
agents).

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | Requested sprints completed; nothing blocked |
| 1 | Validation failed, or a step failed its postcondition twice (§6.3) |
| 2 | Sprint finished (report + vision status written) but tickets need human intervention |

## 6. Orchestrator

### 6.1 Phase derivation (resume)

There is no state file. On every `run`, the orchestrator derives the current
phase from the filesystem, making the loop idempotent and crash-safe. Given
the latest sprint folder (highest `NN`):

| Observed state | Next phase |
|---|---|
| Required files missing (§8.1) | exit 1 |
| No sprint folders, or latest sprint fully complete (all tickets closed, report section present, vision status stamped `NN`) | step 2 (new sprint) — unless stop conditions say halt (§9) |
| Sprint folder exists but no `sprint_focus.md` | step 2, reusing the existing folder |
| `sprint_focus.md` but no `spec.md` | step 3 |
| `spec.md` but no `tickets/` or it is empty | step 4 |
| An open ticket exists (`done: false` and `needs_human_intervention: false`) | step 5 (implement first open ticket) |
| A ticket has `done: true` and `reviewed: false` | step 5 (review that ticket) |
| All tickets closed; report section missing; no `ux_test_plan.md` | step 5.5.1 |
| `ux_test_plan.md` present; report section missing; no `ux_findings.md` | step 5.5.2 |
| `ux_findings.md` first line is `_Ticketized: no_`; report section missing | step 5.5.3 |
| Findings stamped `_Ticketized: yes_`; all tickets closed; `docs/sprint_reports.html` has no `<section id="sprint-NN">` | step 6 |
| Report section present; `vision_status.md` not stamped with sprint `NN` | step 7 |

"Closed" ticket = `done: true` or `needs_human_intervention: true`. The
open-ticket rows keep precedence, so UX tickets route back through the normal
implement loop. The UX rows apply only while the report section is missing —
sprints completed before the UX phase existed (report present, no UX files)
still count as complete, and a pre-feature sprint that crashed between steps
6 and 7 resumes at step 7, not 5.5. A `ux_findings.md` whose first line is
neither stamp value exactly is malformed state → exit 1.

**Cleanup sprints** (§8.8): a latest sprint whose folder matches
`^\d{2}-cleanup$` derives through its own head rows, then joins the shared
tail above (ticket walk → UX rows → report → vision status → next sprint)
unchanged:

| Observed state | Next phase |
|---|---|
| No `spec.md` | step C3 (identify) |
| `spec.md` first line is not a valid candidates stamp | step C3 again — a failed C3 postcondition (retry policy §6.3), never a derivation crash |
| Stamp has `yes` categories whose ticket ID is missing from `tickets/` | step C4 for the first missing category, in ID order |
| All candidate tickets exist (or the stamp is all-`none`) | the shared tail rows, unchanged — an all-`none` sprint lands on the UX rows with zero tickets |

A "missing category" check matches on ticket-ID prefix (`^001-`, `^002-`,
`^003-`); fix tickets (`001.1-...`) cannot exist before their parent, and UX
tickets are numbered after the highest existing ID, so neither confuses it.
Cleanup sprints have no `sprint_focus.md` — the folder name is the focus —
and `cleanup` is a **reserved slug**: the step-2 postcondition rejects a new
normal-sprint folder named exactly `NN-cleanup`.

The sprint-creation decision lives where new-sprint numbering already lives:
when derivation lands on "new sprint", the orchestrator applies flag/cadence
(§5) to decide the type, and for cleanup creates the `NN-cleanup` folder
itself before any agent runs — the type is on disk from the first moment.
The folder creation is uncommitted (git cannot track an empty directory);
resume safety comes from the directory listing, and the first cleanup commit
is C3's spec commit.

Deterministic markers used above:

- **Report**: step 6 must produce exactly one `<section id="sprint-NN">` per
  sprint; presence is checked by string match.
- **Vision status**: the template's first line is
  `_Last updated: sprint NN_`; the orchestrator parses `NN`.
- **UX findings**: the file's first line is exactly `_Ticketized: no_`
  (written by step 5.5.2) until the orchestrator flips it to
  `_Ticketized: yes_` after step 5.5.3.

This derivation is a pure function of filesystem state and must be
unit-tested in isolation.

### 6.2 Sequencing

Steps run strictly sequentially. Each agent invocation is awaited, then its
**postcondition** (per-step, §8) is checked programmatically before the loop
advances.

### 6.3 Failure policy: one retry, then die

If a step's postcondition fails, the orchestrator re-runs the agent **once**,
appending a description of what was expected but not found to the prompt. If
it fails again, exit 1 with a clear message. Never more than one retry —
repeated failure means the prompt or state is wrong, and a human should look.

**Exception — rate/usage limits.** A `claude` run that exits non-zero with a
usage/rate-limit message (detected by `lib/ratelimit.ts`, the only place
allowed to pattern-match `claude` output) is a pause, not a failure: the
spawn wrapper logs one line (how long it will wait and the wall-clock resume
time), sleeps until the reset time parsed from the message plus a margin
(a default wait when no reset time is parseable, always capped by
`maxSingleWaitMs`), and re-runs the **same attempt**. A rate-limited attempt
does not consume the retry — the retry counter only advances on a run that
actually completed (exit 0 → postcondition checked). A zero exit is never
classified, however limit-like its output looks. After `maxConsecutiveWaits`
consecutive rate-limited attempts of one step, exit 1 naming the step and
the count. Killing the process mid-wait is safe as always: no waiting state
is persisted; a rerun derives the same step. Knobs: `RATE_LIMIT` in
`config.ts` (§7).

### 6.4 Git conventions

- Work happens directly on the current branch. No sprint branches, no PRs.
- `.working/` is tracked in git — it is the loop's memory; resume and the
  report depend on it.
- The **orchestrator** commits loop artifacts deterministically after each
  step: `chore(loop): sprint NN focus`, `chore(loop): sprint NN spec`,
  `chore(loop): sprint NN tickets`, ticket-status updates,
  `chore(loop): sprint NN ux plan`, `... ux findings`, `... ux tickets` (the
  tickets commit includes the stamp flip), report, vision status. On cleanup
  sprints, step C4's per-category commits are
  `chore(loop): sprint NN tickets (<category>)` — up to three, greppable.
- The **implement agent** commits code, with the ticket ID in every message:
  `feat(sNN/TTT): <title>` (or `fix(sNN/TTT.1): ...` for fix tickets) — so
  commits ↔ tickets are greppable. On cleanup sprints the three category
  tickets commit as `refactor(sNN/001|002)` / `docs(sNN/003)` instead of
  `feat`; fix tickets keep `fix`, and UX tickets keep `feat` even there — a
  UX fix is not cleanup.
- After each implement run, the orchestrator records the new commit SHAs
  (`git rev-list` of before-HEAD..after-HEAD) into the ticket's `commits`
  array. The review step diffs exactly those commits — not "the last commit".

## 7. Agent invocation

Every agent step spawns a fresh process:

```
claude -p --dangerously-skip-permissions --model <model> --max-turns <n> < filled-prompt
```

- **Prompts** are markdown templates in `scripts/mmm-loop/prompts/`, filled by
  the orchestrator with concrete values (sprint path, ticket path, sprint
  number, ...). Every prompt states: the agent's single purpose, its inputs,
  its exact expected output (files and format), and what NOT to do.
- **Permissions**: `--dangerously-skip-permissions` — the honest name for
  what autonomous means. (If too spicy for a given project, edit the copied
  `config.ts` to use `--permission-mode acceptEdits` plus an allowlist.)
- **Model/effort/max-turns** per step live in `config.ts`:

| Step | Model (default) | Effort | max-turns (default) |
|------|-----------------|--------|---------------------|
| 2 sprint focus | `claude-fable-5` | highest available ("extra") | 50 |
| 3 spec | `claude-fable-5` | extra | 50 |
| C3 cleanup identify | `claude-fable-5` | extra | 75 (exploration-heavy) |
| 4 tickets | `claude-fable-5` | extra | 50 |
| C4 cleanup ticketize | `claude-fable-5` | extra | 50 |
| 5.1 implement | `claude-fable-5` | extra | 150 |
| 5.2 review | `claude-fable-5` | extra | 75 |
| 5.5.1 ux plan | `claude-fable-5` | extra | 50 |
| 5.5.2 ux test | `claude-fable-5` | extra | 100 |
| 5.5.3 ux ticketize | `claude-fable-5` | default | 30 |
| 6 report | `claude-fable-5` | default | 75 |
| 7 vision status | `claude-haiku-4-5` | default | 30 |

Planning, implementation, and review get the strongest model at the highest
reasoning effort; simple mechanical steps may use Haiku. The exact CLI
flag/setting for effort depends on the installed Claude Code version — the
spawn wrapper owns that translation. All values are per-project editable.

Rate/usage-limit handling (§6.3) is configured by one grouped constant in
`config.ts`:

```ts
export const RATE_LIMIT = {
  /** Wait when the error carries no parseable reset time. */
  defaultWaitMs: 30 * 60 * 1000,
  /** Safety margin added on top of a parsed reset time. */
  resetMarginMs: 60 * 1000,
  /** Sanity cap for one wait. */
  maxSingleWaitMs: 12 * 60 * 60 * 1000,
  /** Consecutive rate-limited attempts of one step before giving up. */
  maxConsecutiveWaits: 24,
};
```

The env vars `MMM_LOOP_RL_DEFAULT_WAIT_MS` and `MMM_LOOP_RL_RESET_MARGIN_MS`
override the two wait values, and `MMM_LOOP_RL_MAX_WAITS` overrides
`maxConsecutiveWaits` (env wins; same idiom as `MMM_LOOP_CLAUDE_BIN`) — for
tests and one-off runs.

### Console output

Watching the loop is the product's demo, so the orchestrator's own lines
between agent runs are made legible — strictly cosmetically: prompts, agent
behavior, and timing are untouched. Before each spawn a step banner replaces
the bare phase line: a fixed per-step emoji (typed `Record<StepId, string>`)
plus the phase description verbatim (`🔨 phase: step 5.1 — …`), a dim
metadata line with the step's model/effort/max-turns, and the prompt template
path to open when a step misbehaves; the §6.3 retry reprints the banner with
an `attempt 2/2` marker. After each successful agent step one outcome line
reports wall-clock duration (`✓ step 5.1 done (4m 12s)`); sprint completion
(🎉), cleanup-sprint notices (🧹), blocked exits (⛔), and the final `done.`
(✅) keep their text and gain an emoji. Colors come from a tiny in-repo ANSI
helper (`lib/console.ts`, zero dependencies) and — together with the `──`
banner rules — degrade to plain text when stdout is not a TTY or `NO_COLOR`
is set (checked once), so piped/CI output and the grep contracts
(`[mmm-loop]` prefix on single-line status messages, `phase: <description>`
in every banner) stay stable. The agents' own stdout/stderr is passed
through byte-for-byte (teed live, per §2.1) — no prefixing, recoloring,
buffering, or spinners.

## 8. The steps

### 8.1 Step 1 — Validate (programmatic, no agent)

Checks that these exist (existence only, not content):

- `docs/CONTEXT.md`
- `docs/vision.md`
- `.working/vision_status.md`

Missing any → exit 1 with a message listing exactly which files are missing
and suggesting `init`. Note: `docs/sprint_reports.html` is *generated* by
step 6 and is **not** validated here.

Step 1 also validates the logged-in Claude user when `ALLOWED_CLAUDE_USER`
(§5) is set: the account email is read from Claude Code's own config
(`$CLAUDE_CONFIG_DIR/.claude.json` when set, else `~/.claude.json` — the
mechanism is isolated in one function) and compared case-insensitively,
whitespace trimmed. A mismatch aborts with exit 1 naming both addresses; an
undeterminable user (no config file, no login — e.g. API-key auth, which
has no logged-in account) fails **closed** with exit 1 and guidance
(`/status` inside `claude`, or set the constant back to `null`). Checked
once at startup, before any agent spawns or git operation; an account
switch mid-run is out of scope.

### 8.2 Step 2 — Sprint focus (agent)

**Purpose**: decide what the next sprint should focus on to advance the
vision, and why.

- **Inputs**: `docs/vision.md`, `.working/vision_status.md`,
  `docs/CONTEXT.md`, plus whatever research the agent deems necessary.
- **Output**: `.working/sprints/NN-slug/sprint_focus.md` — a high-level
  description of *what* the sprint focuses on and *why*. One coherent focus
  area, bigger than a single session task but not more (e.g. "building an
  MVP", "implementing authentication", "persisting user data"). The prompt
  instructs the agent to be conservative — small sprints.
- The orchestrator supplies `NN`; the agent chooses the kebab-case slug.
- **Postcondition**: folder matches `^\d{2}-[a-z0-9-]+$`; `sprint_focus.md`
  exists and is non-empty.

Example output:

```md
# Sprint 02 — MVP supporting x and y

## What
An MVP with minimal features supporting x and y...

## Why
To get a minimal working product into production to validate the idea quickly...
```

### 8.3 Step 3 — To specification (agent)

**Purpose**: turn the sprint focus into a spec with clearly stated, testable
goals. Inspired by [to-spec](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md).

- **Inputs**: latest `sprint_focus.md`, `docs/`.
- **Output**: `spec.md` in the sprint folder. The spec contains **no**
  statuses and tracks **no** progress — that is the tickets' job.
- **Postcondition**: `spec.md` exists and is non-empty.

### 8.4 Step 4 — To tickets (agent)

**Purpose**: break the spec into small, ordered, independently completable
tickets. Inspired by [to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)
and ralph's [prd.json](https://github.com/snarktank/ralph/blob/main/prd.json.example).

- **Inputs**: latest `spec.md`, `docs/CONTEXT.md`.
- **Output**: `tickets/NNN-slug.json` files in the sprint folder. Filename
  order is execution order; the loop is sequential, so there is no dependency
  graph — earlier tickets must not depend on later ones.
- **Postcondition**: at least one ticket exists; every ticket parses and
  passes schema validation (below); filenames match
  `^\d{3}(\.\d)?-[a-z0-9-]+\.json$`.

#### Ticket schema

```json
{
  "id": "003",
  "title": "Persist user settings",
  "description": "As a user, I want ... so that ...",
  "tests": [
    { "description": "settings survive restart", "passes": false }
  ],
  "done": false,
  "reviewed": false,
  "needs_human_intervention": false,
  "needs_human_intervention_reason": null,
  "human_note": null,
  "commits": []
}
```

Field ownership:

| Field | Written by |
|---|---|
| `id`, `title`, `description`, `tests[].description` | to-tickets agent (step 4) / review agent for fix tickets |
| `tests[].passes`, `done`, `needs_human_intervention`, `needs_human_intervention_reason` | implement agent (self-reported, §8.5) |
| `reviewed`, `commits` | orchestrator only |
| `human_note` | human only (§10) |

Test verification is **self-reported by the implement agent** — it runs
whatever tests it can (including browser tests etc.), records per-test
`passes`, and flips `done: true` itself. The orchestrator does not run tests;
it only validates JSON shape and state transitions.

### 8.5 Step 5 — Implement loop

While the latest sprint has an open ticket (`done: false` and
`needs_human_intervention: false`), take the first by filename order:

#### 8.5.1 Implement (agent)

Inspired by [implement](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md).

- **Inputs**: the ticket JSON, `spec.md`, `docs/CONTEXT.md`,
  `.working/learnings.md`, and the ticket's `human_note` if set.
- **Work**: implement the ticket; commit code with the conventional message
  (§6.4); run the ticket's tests; update the ticket JSON: set each
  `tests[].passes`, then either `done: true`, or
  `needs_human_intervention: true` with a concrete
  `needs_human_intervention_reason`. May append one-line learnings
  (gotchas, discovered conventions) to `.working/learnings.md`.
- **Postcondition** (orchestrator): ticket JSON still parses; exactly one of
  `done` / `needs_human_intervention` was flipped to `true` (an agent run
  that changes neither is a failed step → retry policy §6.3).
- The orchestrator then records new commit SHAs into `commits` and commits
  the ticket-status change.

#### 8.5.2 Review (agent)

Runs on every ticket that reaches `done: true` with `reviewed: false`.
Inspired by [code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md).

- **Inputs**: the ticket JSON, the exact diff of the ticket's `commits`,
  `spec.md`, `docs/CONTEXT.md`, `.working/learnings.md`.
- **Findings** (problems, simplification, readability, cleaner-code
  opportunities) that are worth fixing become **at most one fix ticket**:
  `NNN.1-<slug>.json`, same schema, with the same (or improved) tests as the
  findings warrant. It sorts directly after its parent and is picked up next
  by the implement loop.
- **Hard bounds against spinning** (one review generation only):
  - Max **one** fix ticket per original ticket.
  - Reviews of fix tickets (`id` contains `.`) never create new tickets:
    remaining findings either set `needs_human_intervention: true` (+ reason)
    on the fix ticket, or are dropped as not worth it.
- No findings → the agent changes nothing; that is a valid outcome.
- The **orchestrator** sets `reviewed: true` after the review run and commits.

#### 8.5.3 Step 5.5 — UX testing

Runs when the implement loop has no open tickets, before step 6. Ticket
review (§8.5.2) is diff-scoped and code-focused — nothing in the loop ever
*uses* what the sprint built the way a user would. This phase closes that gap
autonomously: agents plan, execute, and ticketize a user-experience test of
the sprint's delta before the sprint reports itself done, so fixes land in
the **same sprint** and the report describes the post-fix state.

**UX** means any intended experience for a user of what was produced or
changed during the sprint — *intended* as defined by `spec.md` and
`sprint_focus.md`, adjusted by `.working/learnings.md` (a deviation recorded
in learnings is not a finding). Not limited to browsers: CLI output, API
ergonomics, and docs count when they are the product. Testing is **agentic,
not human**: the test agent exercises the artifact itself; it never produces
manual test scripts for a person to run.

Three sequential agent sub-steps, each with the standard postcondition +
retry policy (§6.3):

| Sub-step | Agent | Output |
|---|---|---|
| 5.5.1 | UX plan | `ux_test_plan.md` in the sprint folder |
| 5.5.2 | UX test | `ux_findings.md` in the sprint folder |
| 5.5.3 | UX ticketize | zero or more `tickets/NNN-ux-slug.json` |

**5.5.1 — UX plan**: identify the sprint's user-facing delta, decide how
(and whether) it can be tested agentically, and produce a concrete plan.
Inputs: the sprint folder (focus, spec, tickets incl. states),
`docs/CONTEXT.md`, `.working/learnings.md`, the sprint's commits, and the
project's run/usage docs. The plan may only rely on tools already available
in the target project and environment — **installing dependencies is out of
bounds**; warranted-but-infeasible testing is recorded under "Not testable".
"Nothing to test" is a valid plan. Postcondition: file exists and is
non-empty.

**5.5.2 — UX test**: execute the plan and record findings in a fixed
template whose first line is exactly `_Ticketized: no_`. Existing tools
only; the agent must not modify project code — its only intended write is
the findings file (scratch/run artifacts are tolerated but never committed).
Infeasible plan items go under "Not testable", never forced. "No findings."
is a valid outcome. Postcondition: file exists; first line is exactly the
stamp.

**5.5.3 — UX ticketize**: turn findings worth fixing into standard-schema
tickets (§8.4), `tests[]` derived from each finding's expected behavior.
Zero tickets is a valid outcome; findings not ticketized simply remain in
the findings file, visible in the report. Numbering continues after the
highest existing `NNN` (fix tickets count via their integer part); the slug
is prefixed `ux-` — filenames match `^\d{3}-ux-[a-z0-9-]+\.json$` — so UX
tickets sort after the sprint's original tickets and are greppable.
Postcondition: every new ticket file parses, passes schema validation, and
matches the filename pattern; existing tickets are untouched. After the
postcondition passes, the **orchestrator** flips the findings stamp to
`_Ticketized: yes_` (orchestrator-owned, like `reviewed`).

**One UX pass per sprint (the anti-spin bound)**: once `ux_test_plan.md` and
`ux_findings.md` exist, derivation never re-enters step 5.5. UX tickets are
implemented and reviewed under the normal rules (including at most one
`NNN.1` fix ticket each), and there is **no re-test** after they close — the
loop proceeds to step 6. There is deliberately **no cap on the number of
tickets** created from findings; the bound against spinning is the single
pass, not a ticket count. Blocked tickets count as closed, so a sprint with
a blocked ticket still gets its UX pass — findings may predate the eventual
human fix (accepted, mirrors the stale-report quirk in §10).

### 8.6 Step 6 — Report and quiz (agent)

**Purpose**: create or edit `docs/sprint_reports.html` — a single
self-contained file (inline CSS/JS, no build step, mermaid or inline SVG for
diagrams) with one section per sprint.

- **Inputs**: the sprint folder (focus, spec, tickets), `ux_findings.md` (if
  present), `.working/learnings.md`, the sprint's commits, the existing
  report file.
- Each sprint section (`<section id="sprint-NN">`, exactly one per sprint —
  the agent must replace its own section if it already exists) contains:
  - Short summary of what the sprint achieved and how the introduced code
    works — text and a diagram.
  - Key decisions taken, prioritizing the least obvious ones.
  - Tickets with `needs_human_intervention: true` — visually prioritized;
    additionally rendered as a banner at the top of the page while any exist.
  - UX findings that were not ticketized, so unfixed experience problems are
    visible to a human.
  - A multiple-choice quiz about the design/architecture/how the code works —
    inline JS, click-to-reveal answers, human-only, no persistence.
- **Postcondition**: file exists and contains `<section id="sprint-NN">` for
  the current sprint.

### 8.7 Step 7 — Update vision status (agent)

**Purpose**: rewrite `.working/vision_status.md` to reflect reality after the
sprint. This file is step 2's main input — drift here compounds into bad
sprint focus, so it uses a **fixed template, replaced (not appended) each
sprint**, capped at ~120 lines:

```md
_Last updated: sprint NN_

# Vision status

## What exists now
## What works (verified)
## Known gaps
## Blocked on human
```

- **Inputs**: previous `vision_status.md`, the sprint folder (including
  `ux_findings.md` if present), `docs/vision.md`.
- Unresolved UX findings (not ticketized, or ticketized but blocked) belong
  under "Known gaps".
- **Postcondition**: first line stamps the current sprint number.

### 8.8 Cleanup sprints — steps C3 and C4

A second sprint type: instead of advancing the vision, a **cleanup sprint**
finds and executes the most obvious improvement in each of three categories —
architecture, clean code, docs — reusing the existing
ticket/implement/review/UX/report machinery unchanged. Why: debt accretes by
construction (review is diff-scoped, so cross-cutting drift is invisible to
it), and the loop eats its own docs — stale `docs/` compounds into worse
sprint focus. It is a sprint *type*, not a step, so it costs nothing when not
triggered. The bar is deliberately high: LLM-initiated "improvements" churn
easily, so candidates must be obvious, certain, single-ticket-feasible wins —
**finding nothing is a valid, successful outcome**, and an empty sprint is
cheap. Triggering and scheduling live in §5; on-disk representation and
derivation in §6.1. Steps C3/C4 replace steps 2–4; everything from the
implement loop on runs unchanged.

#### C3 — Identify candidates (agent; replaces steps 2–3)

- **Categories**:
  1. **architecture** — structural improvement of the codebase.
  2. **clean-code** — readability/simplification/duplication in code.
  3. **docs** — any project documentation: `README`, `docs/`,
     `docs/CONTEXT.md`, `.working/learnings.md` (pruning/dedup), inline code
     docs. **`docs/vision.md` is off-limits** — human-authored north star,
     never edited by the loop (read-only input for relevance judgment).
- **At most one candidate per category.** A candidate must be an obvious,
  certain win — feasible as a single ticket and relevant to the project's
  current state. If nothing clears the bar, the category is skipped; the
  prompt states explicitly that skipping is the expected outcome for a
  healthy area.
- **Inputs**: `docs/CONTEXT.md`, `docs/vision.md` (read-only),
  `.working/vision_status.md`, `.working/learnings.md`, free exploration of
  the codebase and recent sprint folders (blocked-ticket reasons are a
  strong signal of problem areas).
- **Output**: `spec.md` in the sprint folder. Its **first line** is a
  machine-readable candidates stamp (same idiom as the vision-status stamp):

  ```
  _Candidates: architecture=yes, clean-code=none, docs=yes_
  ```

  Exact format: the three keys in that order, each valued `yes` or `none`.
  The body must contain a section per `yes` category describing: what the
  improvement is, which files it touches, why it is a clear win, and why it
  fits in one ticket.
- **Postcondition**: `spec.md` exists; first line parses as the stamp. (The
  stamp is the contract; body content is the prompt's job.)
- Committed as `chore(loop): sprint NN spec`, like step 3.

#### C4 — Ticketize (agents; replaces step 4)

One agent invocation **per `yes` category**, run sequentially in category
order (the outer derive→run→re-derive cycle produces the sequence). Each
produces exactly one ticket with a **fixed ID per category**:

| Category | Ticket ID | Runs |
|---|---|---|
| architecture | `001` | first |
| clean-code | `002` | second |
| docs | `003` | last |

Structural change first; docs last, so they document the post-cleanup state.
Absent categories simply leave a gap in the IDs — the ticket walk is
filename-ordered and does not assume contiguity, so C4's postcondition
deliberately has no contiguity check (unlike step 4's).

- **Inputs**: `spec.md` (its category's section), `docs/CONTEXT.md`,
  `.working/learnings.md`.
- **Output**: `tickets/NNN-slug.json`, existing schema (§8.4) unchanged.
  Tests for refactor tickets include "all existing tests still pass"; tests
  for docs tickets are concrete checks ("statement X in README matches
  actual CLI behavior").
- **Postcondition** (per invocation): exactly one new ticket file with the
  category's fixed ID exists, parses, passes schema validation; existing
  files untouched.
- **Zero `yes` categories** → C4 does not run at all; the sprint proceeds
  down the shared tail with empty `tickets/`: the UX pass (§8.5.3) runs as
  usual — with no delta it concludes "nothing to test" quickly — then the
  report. Quick but not free, by choice: skipping would special-case the
  tail.

#### Unchanged machinery, small deltas

- **Implement + review loop (§8.5)**: unchanged, including fix tickets and
  their hard bounds. Commit-type delta per §6.4.
- **UX testing (§8.5.3)**: runs unchanged — no special-casing, not even for
  zero-candidate sprints. Cleanup must not change behavior, so the UX pass
  doubles as a regression check on that promise.
- **Report (§8.6)**: unchanged postcondition. The prompt receives a
  sprint-type section: for cleanup sprints, summarize improvements instead
  of feature work; for a zero-candidate sprint the section states that
  identification found nothing worth cleaning — that *is* the summary.
- **Vision status (§8.7)**: runs unchanged. Content mostly carries over
  (cleanup doesn't advance the vision), but the stamp is still required —
  derivation's completeness check depends on it.
- **Outer loop, stop conditions, exit codes (§5, §9)**: unchanged. Blocked
  cleanup tickets → exit 2 like any others.

## 9. Outer loop and stop conditions

After step 7:

1. If any ticket in the finished sprint has `needs_human_intervention: true`
   → **exit 2**. (The report already surfaces what's blocked; a new sprint
   would likely hit the same wall and burn tokens.)
2. Else, if fewer than `--max-sprints` sprints have completed this run
   → back to step 2.
3. Else → **exit 0**.

There is no LLM judgment in the control path ("is the vision done?" is not a
stop condition). Fully lights-off: no human gates before implementation (a
deliberate ralph-over-wsff choice); the mitigations are conservative
sprint-focus prompting and `--max-sprints 1` as the default, so a human
reviews between runs. Design so that an opt-in `--pause-after focus|spec`
flag is trivial to add later — it falls out of filesystem-derived resume.

## 10. Human workflow for blocked tickets

1. Read the report (blocked items are the top banner) or grep tickets for
   `"needs_human_intervention": true`.
2. Edit the ticket JSON directly: set `needs_human_intervention: false` and
   write guidance into `human_note`.
3. Rerun `bun scripts/mmm-loop/loop.ts run` — phase derivation lands back in
   step 5 and the implement agent's prompt includes the `human_note`.

Two accepted staleness quirks of this workflow: the report was written while
the ticket was still blocked and is not regenerated after the resume, and
the sprint's `ux_findings.md` (written when all tickets were closed, §8.5.3)
may predate the final code state for the sprint — the UX pass is
single-shot and does not rerun.

## 11. Learnings file

`.working/learnings.md` — append-only one-liners written by implement/review
agents ("gotchas, conventions discovered"), included in every implement and
review prompt. Ralph's highest-value trick, adopted wholesale.

## 12. Out of scope (v1) / future candidates

- `--pause-after focus|spec` human gate (fast-follow; design keeps it trivial)
- `mmm-loop unblock <ticket-id>` interactive command
- `--continue-on-blocked` flag
- Dependency graphs between tickets (order stays linear)
- Orchestrator-run test commands (deliberately rejected — self-report chosen)
- More than one cleanup candidate per category; per-category cadences
- Cross-sprint cleanup memory ("we deferred X last time") beyond what
  `.working/learnings.md` already provides
