# mmm-loop — Specification

An autonomous, sprint-based agent loop for Claude Code. This document is the
source of truth for the design; code comments reference its sections
(`spec §N`). The [README](../README.md) covers installation and usage.

Inspirations: [wsff](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md),
[mattpocock/skills](https://github.com/mattpocock/skills),
[ralph](https://github.com/snarktank/ralph).

---

## 1. Overview

mmm-loop runs an unattended development loop against a target project. Each
iteration is a **sprint**: pick a focus area from the vision, write a spec,
break it into tickets, implement and review each ticket, produce an HTML
report with a quiz, and update the project's vision status. The loop then
halts (default: one sprint per invocation) or starts the next sprint.

A deterministic **orchestrator** (TypeScript on Bun) drives the loop. All
control flow — file validation, phase selection, ticket ordering, commit
recording, stop conditions — is plain code. LLM agents (fresh `claude -p`
processes) are used only for the creative work inside each step.

## 2. Design principles

1. **Autonomous** — runs without human intervention; humans interact only
   between runs (report, blocked tickets).
2. **Deterministic where possible** — anything checkable programmatically is
   checked by the orchestrator, never delegated to an LLM.
3. **Sequential** — each step finishes (and is validated) before the next
   starts. Within step 5, one ticket at a time.
4. **Minimal context** — each agent gets a fresh process, a purpose-built
   prompt, and only the files it needs.
5. **Focused agents** — every prompt states the agent's single purpose and
   exact expected output.
6. **Self-contained per project** — the loop's scripts and prompts are copied
   into each target project (ralph-style), so they are visible and freely
   modifiable per project.
7. **Crash-safe** — the current phase is derived from filesystem state, so the
   loop can be killed and rerun at any point without losing or orphaning work.

## 3. Distribution and installation

The mmm-loop repo contains a copyable bundle at `scripts/mmm-loop/`. To
install into a target project:

```bash
cp -r <mmm-loop-repo>/scripts/mmm-loop <target>/scripts/mmm-loop
```

Then, from the target project root:

```bash
bun scripts/mmm-loop/loop.ts init   # scaffold required files
bun scripts/mmm-loop/loop.ts run    # run one sprint
```

There is no global install and no version coupling: the copy is yours to edit.
Prompts ship inside the bundle, so per-project prompt tweaks are normal and
expected.

### Bundle layout (copied into the target project)

```
scripts/mmm-loop/
  loop.ts            # entry point: init | run
  config.ts          # per-step model / effort / max-turns table (edit freely)
  lib/               # orchestrator internals (phase derivation, spawn wrapper, ...)
  prompts/
    02-sprint-focus.md
    03-spec.md
    04-tickets.md
    05-implement.md
    05-review.md
    06-report.md
    07-vision-status.md
```

## 4. Target project layout

```
docs/
  CONTEXT.md               # always-relevant context for every agent (human-authored)
  vision.md                # what to build (human-authored)
  sprint_reports.html      # generated by step 6 (not required by validation)
  ...                      # optionally other human docs
.working/                  # the loop's memory — tracked in git, NOT gitignored
  vision_status.md         # current state of the project vs the vision
  learnings.md             # append-only one-liners (gotchas, conventions)
  sprints/
    01-mvp/
      sprint_focus.md
      spec.md
      tickets/
        001-first-thing.json
        001.1-fix-first-thing.json     # optional review fix ticket
        002-second-thing.json
```

- Sprint folders: `NN-slug` — two-digit zero-padded number + kebab-case slug,
  so lexical sort equals numeric sort. `NN` = existing sprint folder count + 1.
- Ticket files: `NNN-slug.json` (three-digit). Execution order = filename
  order. Fix tickets are `NNN.1-slug.json`, which sorts directly after the
  parent (`003-x.json` < `003.1-fix-x.json` < `004-y.json`); the filename
  itself encodes parentage — there is no `parent` field.

## 5. CLI

### `init`

Scaffolds the required files with template content (headings plus TODO
placeholders and short suggestions of what to write). Never overwrites an
existing file. Creates:

- `docs/CONTEXT.md`
- `docs/vision.md`
- `.working/vision_status.md` (template from §8.7, stating nothing is built yet)
- `.working/learnings.md` (empty with a one-line header)

### `run [--max-sprints N]`

Runs the loop. Default `--max-sprints 1`: one full sprint, then exit. Higher
values chain sprints (e.g. `--max-sprints 3` for an overnight run) — but a
sprint that ends with blocked tickets always halts the run (§9), regardless of
sprints remaining.

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | Requested sprints completed; nothing blocked |
| 1 | Validation failed, or a step failed its postcondition twice (§6.3) |
| 2 | Sprint finished (report + vision status written) but tickets need human intervention |

## 6. Orchestrator

### 6.1 Phase derivation (resume)

There is no state file. On every `run`, the orchestrator derives the current
phase from the filesystem, making the loop idempotent and crash-safe. Given
the latest sprint folder (highest `NN`):

| Observed state | Next phase |
|---|---|
| Required files missing (§8.1) | exit 1 |
| No sprint folders, or latest sprint fully complete (all tickets closed, report section present, vision status stamped `NN`) | step 2 (new sprint) — unless stop conditions say halt (§9) |
| Sprint folder exists but no `sprint_focus.md` | step 2, reusing the existing folder |
| `sprint_focus.md` but no `spec.md` | step 3 |
| `spec.md` but no `tickets/` or it is empty | step 4 |
| An open ticket exists (`done: false` and `needs_human_intervention: false`) | step 5 (implement first open ticket) |
| A ticket has `done: true` and `reviewed: false` | step 5 (review that ticket) |
| All tickets closed; `docs/sprint_reports.html` has no `<section id="sprint-NN">` | step 6 |
| Report section present; `vision_status.md` not stamped with sprint `NN` | step 7 |

"Closed" ticket = `done: true` or `needs_human_intervention: true`.

Deterministic markers used above:

- **Report**: step 6 must produce exactly one `<section id="sprint-NN">` per
  sprint; presence is checked by string match.
- **Vision status**: the template's first line is
  `_Last updated: sprint NN_`; the orchestrator parses `NN`.

This derivation is a pure function of filesystem state and must be
unit-tested in isolation.

### 6.2 Sequencing

Steps run strictly sequentially. Each agent invocation is awaited, then its
**postcondition** (per-step, §8) is checked programmatically before the loop
advances.

### 6.3 Failure policy: one retry, then die

If a step's postcondition fails, the orchestrator re-runs the agent **once**,
appending a description of what was expected but not found to the prompt. If
it fails again, exit 1 with a clear message. Never more than one retry —
repeated failure means the prompt or state is wrong, and a human should look.

### 6.4 Git conventions

- Work happens directly on the current branch. No sprint branches, no PRs.
- `.working/` is tracked in git — it is the loop's memory; resume and the
  report depend on it.
- The **orchestrator** commits loop artifacts deterministically after each
  step: `chore(loop): sprint NN focus`, `chore(loop): sprint NN spec`,
  `chore(loop): sprint NN tickets`, ticket-status updates, report, vision
  status.
- The **implement agent** commits code, with the ticket ID in every message:
  `feat(sNN/TTT): <title>` (or `fix(sNN/TTT.1): ...` for fix tickets) — so
  commits ↔ tickets are greppable.
- After each implement run, the orchestrator records the new commit SHAs
  (`git rev-list` of before-HEAD..after-HEAD) into the ticket's `commits`
  array. The review step diffs exactly those commits — not "the last commit".

## 7. Agent invocation

Every agent step spawns a fresh process:

```
claude -p --dangerously-skip-permissions --model <model> --max-turns <n> < filled-prompt
```

- **Prompts** are markdown templates in `scripts/mmm-loop/prompts/`, filled by
  the orchestrator with concrete values (sprint path, ticket path, sprint
  number, ...). Every prompt states: the agent's single purpose, its inputs,
  its exact expected output (files and format), and what NOT to do.
- **Permissions**: `--dangerously-skip-permissions` — the honest name for
  what autonomous means. (If too spicy for a given project, edit the copied
  `config.ts` to use `--permission-mode acceptEdits` plus an allowlist.)
- **Model/effort/max-turns** per step live in `config.ts`:

| Step | Model (default) | Effort | max-turns (default) |
|------|-----------------|--------|---------------------|
| 2 sprint focus | `claude-fable-5` | highest available ("extra") | 50 |
| 3 spec | `claude-fable-5` | extra | 50 |
| 4 tickets | `claude-fable-5` | extra | 50 |
| 5.1 implement | `claude-fable-5` | extra | 150 |
| 5.2 review | `claude-fable-5` | extra | 75 |
| 6 report | `claude-fable-5` | default | 75 |
| 7 vision status | `claude-haiku-4-5` | default | 30 |

Planning, implementation, and review get the strongest model at the highest
reasoning effort; simple mechanical steps may use Haiku. The exact CLI
flag/setting for effort depends on the installed Claude Code version — the
spawn wrapper owns that translation. All values are per-project editable.

## 8. The steps

### 8.1 Step 1 — Validate (programmatic, no agent)

Checks that these exist (existence only, not content):

- `docs/CONTEXT.md`
- `docs/vision.md`
- `.working/vision_status.md`

Missing any → exit 1 with a message listing exactly which files are missing
and suggesting `init`. Note: `docs/sprint_reports.html` is *generated* by
step 6 and is **not** validated here.

### 8.2 Step 2 — Sprint focus (agent)

**Purpose**: decide what the next sprint should focus on to advance the
vision, and why.

- **Inputs**: `docs/vision.md`, `.working/vision_status.md`,
  `docs/CONTEXT.md`, plus whatever research the agent deems necessary.
- **Output**: `.working/sprints/NN-slug/sprint_focus.md` — a high-level
  description of *what* the sprint focuses on and *why*. One coherent focus
  area, bigger than a single session task but not more (e.g. "building an
  MVP", "implementing authentication", "persisting user data"). The prompt
  instructs the agent to be conservative — small sprints.
- The orchestrator supplies `NN`; the agent chooses the kebab-case slug.
- **Postcondition**: folder matches `^\d{2}-[a-z0-9-]+$`; `sprint_focus.md`
  exists and is non-empty.

Example output:

```md
# Sprint 02 — MVP supporting x and y

## What
An MVP with minimal features supporting x and y...

## Why
To get a minimal working product into production to validate the idea quickly...
```

### 8.3 Step 3 — To specification (agent)

**Purpose**: turn the sprint focus into a spec with clearly stated, testable
goals. Inspired by [to-spec](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md).

- **Inputs**: latest `sprint_focus.md`, `docs/`.
- **Output**: `spec.md` in the sprint folder. The spec contains **no**
  statuses and tracks **no** progress — that is the tickets' job.
- **Postcondition**: `spec.md` exists and is non-empty.

### 8.4 Step 4 — To tickets (agent)

**Purpose**: break the spec into small, ordered, independently completable
tickets. Inspired by [to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)
and ralph's [prd.json](https://github.com/snarktank/ralph/blob/main/prd.json.example).

- **Inputs**: latest `spec.md`, `docs/CONTEXT.md`.
- **Output**: `tickets/NNN-slug.json` files in the sprint folder. Filename
  order is execution order; the loop is sequential, so there is no dependency
  graph — earlier tickets must not depend on later ones.
- **Postcondition**: at least one ticket exists; every ticket parses and
  passes schema validation (below); filenames match
  `^\d{3}(\.\d)?-[a-z0-9-]+\.json$`.

#### Ticket schema

```json
{
  "id": "003",
  "title": "Persist user settings",
  "description": "As a user, I want ... so that ...",
  "tests": [
    { "description": "settings survive restart", "passes": false }
  ],
  "done": false,
  "reviewed": false,
  "needs_human_intervention": false,
  "needs_human_intervention_reason": null,
  "human_note": null,
  "commits": []
}
```

Field ownership:

| Field | Written by |
|---|---|
| `id`, `title`, `description`, `tests[].description` | to-tickets agent (step 4) / review agent for fix tickets |
| `tests[].passes`, `done`, `needs_human_intervention`, `needs_human_intervention_reason` | implement agent (self-reported, §8.5) |
| `reviewed`, `commits` | orchestrator only |
| `human_note` | human only (§10) |

Test verification is **self-reported by the implement agent** — it runs
whatever tests it can (including browser tests etc.), records per-test
`passes`, and flips `done: true` itself. The orchestrator does not run tests;
it only validates JSON shape and state transitions.

### 8.5 Step 5 — Implement loop

While the latest sprint has an open ticket (`done: false` and
`needs_human_intervention: false`), take the first by filename order:

#### 8.5.1 Implement (agent)

Inspired by [implement](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md).

- **Inputs**: the ticket JSON, `spec.md`, `docs/CONTEXT.md`,
  `.working/learnings.md`, and the ticket's `human_note` if set.
- **Work**: implement the ticket; commit code with the conventional message
  (§6.4); run the ticket's tests; update the ticket JSON: set each
  `tests[].passes`, then either `done: true`, or
  `needs_human_intervention: true` with a concrete
  `needs_human_intervention_reason`. May append one-line learnings
  (gotchas, discovered conventions) to `.working/learnings.md`.
- **Postcondition** (orchestrator): ticket JSON still parses; exactly one of
  `done` / `needs_human_intervention` was flipped to `true` (an agent run
  that changes neither is a failed step → retry policy §6.3).
- The orchestrator then records new commit SHAs into `commits` and commits
  the ticket-status change.

#### 8.5.2 Review (agent)

Runs on every ticket that reaches `done: true` with `reviewed: false`.
Inspired by [code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md).

- **Inputs**: the ticket JSON, the exact diff of the ticket's `commits`,
  `spec.md`, `docs/CONTEXT.md`, `.working/learnings.md`.
- **Findings** (problems, simplification, readability, cleaner-code
  opportunities) that are worth fixing become **at most one fix ticket**:
  `NNN.1-<slug>.json`, same schema, with the same (or improved) tests as the
  findings warrant. It sorts directly after its parent and is picked up next
  by the implement loop.
- **Hard bounds against spinning** (one review generation only):
  - Max **one** fix ticket per original ticket.
  - Reviews of fix tickets (`id` contains `.`) never create new tickets:
    remaining findings either set `needs_human_intervention: true` (+ reason)
    on the fix ticket, or are dropped as not worth it.
- No findings → the agent changes nothing; that is a valid outcome.
- The **orchestrator** sets `reviewed: true` after the review run and commits.

### 8.6 Step 6 — Report and quiz (agent)

**Purpose**: create or edit `docs/sprint_reports.html` — a single
self-contained file (inline CSS/JS, no build step, mermaid or inline SVG for
diagrams) with one section per sprint.

- **Inputs**: the sprint folder (focus, spec, tickets), `.working/learnings.md`,
  the sprint's commits, the existing report file.
- Each sprint section (`<section id="sprint-NN">`, exactly one per sprint —
  the agent must replace its own section if it already exists) contains:
  - Short summary of what the sprint achieved and how the introduced code
    works — text and a diagram.
  - Key decisions taken, prioritizing the least obvious ones.
  - Tickets with `needs_human_intervention: true` — visually prioritized;
    additionally rendered as a banner at the top of the page while any exist.
  - A multiple-choice quiz about the design/architecture/how the code works —
    inline JS, click-to-reveal answers, human-only, no persistence.
- **Postcondition**: file exists and contains `<section id="sprint-NN">` for
  the current sprint.

### 8.7 Step 7 — Update vision status (agent)

**Purpose**: rewrite `.working/vision_status.md` to reflect reality after the
sprint. This file is step 2's main input — drift here compounds into bad
sprint focus, so it uses a **fixed template, replaced (not appended) each
sprint**, capped at ~120 lines:

```md
_Last updated: sprint NN_

# Vision status

## What exists now
## What works (verified)
## Known gaps
## Blocked on human
```

- **Inputs**: previous `vision_status.md`, the sprint folder, `docs/vision.md`.
- **Postcondition**: first line stamps the current sprint number.

## 9. Outer loop and stop conditions

After step 7:

1. If any ticket in the finished sprint has `needs_human_intervention: true`
   → **exit 2**. (The report already surfaces what's blocked; a new sprint
   would likely hit the same wall and burn tokens.)
2. Else, if fewer than `--max-sprints` sprints have completed this run
   → back to step 2.
3. Else → **exit 0**.

There is no LLM judgment in the control path ("is the vision done?" is not a
stop condition). Fully lights-off: no human gates before implementation (a
deliberate ralph-over-wsff choice); the mitigations are conservative
sprint-focus prompting and `--max-sprints 1` as the default, so a human
reviews between runs. Design so that an opt-in `--pause-after focus|spec`
flag is trivial to add later — it falls out of filesystem-derived resume.

## 10. Human workflow for blocked tickets

1. Read the report (blocked items are the top banner) or grep tickets for
   `"needs_human_intervention": true`.
2. Edit the ticket JSON directly: set `needs_human_intervention: false` and
   write guidance into `human_note`.
3. Rerun `bun scripts/mmm-loop/loop.ts run` — phase derivation lands back in
   step 5 and the implement agent's prompt includes the `human_note`.

## 11. Learnings file

`.working/learnings.md` — append-only one-liners written by implement/review
agents ("gotchas, conventions discovered"), included in every implement and
review prompt. Ralph's highest-value trick, adopted wholesale.

## 12. Out of scope (v1) / future candidates

- `--pause-after focus|spec` human gate (fast-follow; design keeps it trivial)
- `mmm-loop unblock <ticket-id>` interactive command
- `--continue-on-blocked` flag
- Dependency graphs between tickets (order stays linear)
- Orchestrator-run test commands (deliberately rejected — self-report chosen)
